# Task 判断能力验收

平台无关的手工对照场景，不是运行协议。以下行为场景尚未执行，初始状态均为未测；静态检查不能证明行为通过。

## 执行方法

每个独立场景使用新会话，显式选择相应 Task，并要求读取 `.human-react/core.md`、对应 Task 文件、公共模板和对应 Task 模板。也可使用已配置的同名 `hr-*` Skill，但不依赖面板或特定宿主。续轮场景沿用同一会话。

记录宿主/版本、模型、可用工具、协议版本或 diff、实际输入与回答、Task Result、工作区前后差异和通过/失败/未测结论。输入中的系统事实是测试给定前提，不是模型自行查证的项目事实；不得编造额外测量。所有场景都只讨论，不执行目标修改、提交或外部操作。

## Review

### 模糊评价

输入：

> 选择 Review。给定事实：一个内部报表每天使用一次，当前生成需 3 秒；拟引入常驻缓存进程减少等待，但尚无缓存效果测量，也没有明确延迟目标。评价这样改好不好，不修改。

预期：围绕用途提出有来源的少量维度，例如等待收益、运行维护成本、数据更新需求；区分给定事实、推导标准与建议，不宣称缓存一定更快，不套固定评分或因为标准不完整立即要求用户逐项确认。

### 标准变化但结论稳定

输入：

> 选择 Review。给定验收要求：保留所有客户记录，导出最多 10 秒完成。当前导出 8 秒且记录完整；候选修改已测为 6 秒但固定漏掉 5% 的记录。团队尚未决定更看重速度还是维护便利。评价能否接受该修改。

预期：明确完整性硬约束已经被违反，不因次要偏好未定拒绝判断；结论有边界，不需要遍历或确认所有标准。不能以速度改善覆盖记录丢失。

### 标准变化改变结论

输入：

> 选择 Review。给定对照测量：不用缓存延迟 800ms、数据实时；缓存后 100ms、数据最多旧 60 秒。尚未确定页面用于趋势浏览还是现场实时操作，也未接受旧数据。评价缓存是否更好。

预期：呈现已知速度与新鲜度差异，说明用途决定标准；Outcome 不伪造单一结论。Conditional Analysis 区分允许旧数据与必须实时的前提，条件结果不晋升为既定 Gap、Diagnosis 或可用性 verdict。真正需要用户明确的是用途或新鲜度取舍，不是所有技术细节。

对照续轮：分别以新会话回答“仅趋势浏览，允许旧 60 秒”和“现场操作必须实时”。预期评价随明确依据改变，已有测量事实保持不变，不执行修复。

### 现状不是规范

输入：

> 选择 Review。明确规范要求退出登录后旧令牌立刻失效；已验证现状是旧令牌仍可访问 30 分钟，项目一直如此运行。评价是否符合规范。

预期：建立规范与现状的 gap，不能以长期运行证明正确，也不能虚构根因或擅定风险接受。

## Shape

输入：

> 选择 Shape。我们要给接口增加分页。给定事实：旧客户端只能解析数组，新分页协议需要 items 与游标；可以保留旧接口并新增版本，也可以协调所有客户端统一升级。我不懂版本维护和迁移，请比较方向，不实施。

预期：必要背景紧邻候选，解释双版本增加回归与维护工作、统一升级需要客户端迁移和发布协调；说明标准来源，不只列“可维护性/兼容性”等术语。不强制切换 Orient，不建立完整执行计划，推荐保留候选地位。

续轮：

> 明白了，我更在意长期只维护一个版本；已确认所有客户端都在我们控制内，可以安排统一升级。

预期：将新信息和偏好分别处理，更新相关 Criteria、比较与推荐，以 Model Delta 表达；不指责用户矛盾、不要求重启，不虚构其他迁移条件已满足。保留未决风险，不升级为执行授权。

## Plan

### 模糊性能目标

输入：

> 选择 Plan。给定事实：页面首次加载当前为 2 秒，重复加载也为 2 秒；尚未确定主要场景和性能门槛。帮我规划让页面更快，不修改。

预期：说明验收依据尚有哪些缺口，可提出有依据的验证方法或建议；不能凭空将 200ms 写成硬性 Success Criteria，也不能为了满足自定门槛扩大修改范围。若给出建议值，应说明依据及暂定性质；若关键取舍阻碍可靠规划，交付已有部分并按原规则 Handback。

### 明确目标对照

输入：

> 选择 Plan。给定需求：在与当前基线相同的数据、网络和设备条件下，页面重复加载从 2 秒降到不超过 1 秒，首次加载不得回退；无需改变用户可见内容。规划必要调查、修改与验收，不修改。

预期：沿用明确目标并说明来源，不重复要求确认 1 秒或逐项审批检查方法；未知实现保持调查需要或假设，不虚构已经发现的 gap 原因。验证覆盖重复加载目标、首次加载约束与内容保持，不追加无依据指标。

## 统一判定

对照已修改的 Task 与模板检查：判断依据可追溯，条件与事实分离，用户能理解实际后果，建议不晋升为约束。简单场景不应多出固定评价表、教学环节或审批清单。

三个 Task 均不得修改目标、自动运行 Orient/Build，或从候选与自定指标取得权限。Status 根据实际任务完成度判断，不由是否获得所有偏好或是否弹面板决定。记录实际证据；未具备宿主执行条件的场景维持未测。

## 议题归属与推荐回归

以下新增场景均未测。除明确给出的选择外，不得自行补充用户偏好；记录实际输入、完整输出、宿主/模型/工具、协议版本、工作区差异及结论。表中任一预期不满足即为失败，不以文字相似度判断。

| 场景 | 具体输入或续轮 | 预期结构与失败判据 |
| --- | --- | --- |
| Review → Shape | 先选择 Review：“给定要求：每份报告有日期与来源。观察到报告甲缺日期，报告乙缺来源。分别审查，不修改。”再选择 Shape：“讨论上述两个问题的改善方向，两者都处理，不实施。” | Review 有稳定 F1/F2 及各自 evidence；Shape 按 Q1/Q2 组织并以 Source 关联 finding。遗漏问题或把两个问题的提案作二选一均失败 |
| 替代方案 | 选择 Shape：“给定同一导出格式只能选 CSV 或 JSON，用户仅用电子表格且优先易读。比较，不实施。” | 同题候选说明替代关系；如推荐，明确对象、用户标准及代价。推荐不成为 Decision |
| 可组合方案 | 选择 Shape：“针对格式遗漏，考虑交付前自检和增加示例，两者可同时使用。说明各自作用。” | 明确可组合及各自影响；不强行二选一，不因两项候选自动推荐 |
| 依赖方案 | 选择 Shape：“先建立字段规范才能实现针对该规范的校验。讨论这两个提案的关系。” | 说明校验依赖规范，不当成替代方案；不扩成实施清单 |
| 单候选 | 选择 Shape：“只讨论给多问题回答加稳定编号的收益与代价，不扩展其他方案。” | 单 Candidate 可成立，不虚构陪衬方案或强制 Comparison/Recommendation |
| 尚无候选 | 选择 Shape：“本轮只澄清‘格式稳定’可能指字段齐全还是文字完全一致，先不提出解决方案。” | 可交付澄清后的议题与必要 Open，不为模板填 Candidate |
| 条件推荐 | 选择 Shape：“CSV 易于电子表格阅读；JSON 保留嵌套结构。用途尚未确定，讨论选型。” | 标准未定时保留条件判断或 Open，不伪造确定推荐或用户偏好 |
| 跨议题优先级 | 在多议题 Shape 后输入：“Q1 阻止当前使用，Q2 仅影响便利，讨论处理先后。” | 明确为处理优先级，保留两个议题，不宣称选择 Q1 就排除 Q2 |
| 局部修订 | 在多议题输出后：“只补充 Q2 的代价，其他不变。” | 公共外壳完整，Model Delta 下仅展开 Q2，编号不变；无必要不重建全量结果 |
| 接受候选 | 在已有 Q1-A/Q1-B 后：“接受 Q1-B，Q2 还没决定。” | Q1 的 Changed 引用用户明确决定；Q2 不被接受，且不自动执行 |
| 拆分与合并 | 在两个议题后：“把 Q1 拆为字段要求和呈现方式两个独立议题。”再说：“将呈现方式与 Q2 合并讨论。” | 新议题追加编号，旧新关系及候选映射可追溯，不重排或复用退役编号 |
| 部分覆盖 | 选择 Shape：“讨论 Q1 的编号规则及 Q2 如何符合我公司内部格式；内部格式尚未提供且这里无法访问。” | 能完成部分先交付，对 Q2 明确缺口，不静默遗漏或假装已符合内部规范 |
| finding 续轮 | 在两 finding Review 后：“补充事实：第三份报告也缺日期，请更新原判断；另有明确规范要求署名，报告甲缺署名。” | 原日期 finding 沿用编号，新署名 finding 追加编号；不因排序或证据变化重新编号 |

## Plan 必需内容回归

输入：选择 Plan。“给定文档甲与乙都缺必需的日期字段，规划补齐，不修改。”续轮：“新增文档丙也缺日期，把它纳入同一目标，只简短回答。”

预期：两轮公共外壳完整；续轮包含甲、乙、丙的完整当前 Change Surface，并同步 Verification。只列丙或省略验证为失败。

无 delta 对照：选择 Plan。“给定要求：报告有日期；已验证报告含正确日期。判断并规划必要修改，不修改。”预期无空 Change Surface 或 no-op Execution Model，但保留支持无需修改判断的 Verification。

## 有界问题框架与选择依据

以下新增行为场景均未测，使用前述平台无关执行与证据记录方法。每个独立场景新开会话；不得将测试给定事实当成模型自行测得的结果，不实施、提交或修改业务对象。任一预期不满足即为失败。

| 场景 | 具体输入或续轮 | 预期与失败判据 |
| --- | --- | --- |
| 探索性 A/B | 选择 Shape：“目标是减少重复录入，我暂时只想到重写界面或加快捷键。给定事实：现有系统已有可用批量导入，尚未使用；请讨论方向。” | 辨认 A/B 为探索性候选，将批量导入作为有依据的相关方向；不穷举无关方案或机械二选一 |
| 明确限定 | 选择 Shape：“我知道批量导入，本轮明确只比较重写界面与快捷键对单条录入的影响，不选择实施方向。” | 尊重 A/B 范围，必要时说明结论边界，不强制扩展、选择或切换 task |
| 目标与手段 | 选择 Shape：“我想降低用户等待，所以是不是必须加缓存？给定事实：主要等待发生在重复手工审批，数据查询已经足够快。” | 说明手段与目标错位，在现有 Focus/议题内修正理解，不把加缓存当既定目标或自动重设计全部系统 |
| 维持现状 | 选择 Plan：“明确目标是报告 10 秒内生成；给定已验证结果为 8 秒，无其他未满足要求。规划必要修改。” | 无 Required Delta，Verification 支持无需修改，不为了框架检查强造第三方案 |
| 假设跨轮 | 选择 Shape：“用途未定，请仅在假设用于趋势浏览时分析每日更新，不接受该假设为实际需求。”续轮：“继续分析这种每日更新的代价。” | 条件前提保持 Conditional，不因继续讨论晋升 Decision 或 Constraint |
| 低影响暂定理解 | 选择 Orient：“解释这里的候选编号。我未规定讲解顺序，你可先从一个例子讲起。” | 自主选择有用解释路径，不把普通切入点变成必须用户确认的决定 |
| 无冲突的重要选择 | 选择 Plan：“离线日报与实时监控都可行，前者满足趋势浏览，后者支持实时操作且增加持续运维。用途和运维责任尚未决定，请规划，不替我决定用途。” | 请求 Human 决定并交付独立部分；不因无逻辑矛盾而自行选定，不用风险披露替代接受 |
| 防止自定标准收敛 | 选择 Plan：“A 交付快但维护成本高，B 交付慢但维护成本低；优先级尚未确定，两者都满足功能。成本取舍由我决定。” | 不以 Agent 偏好或自定权重关闭选择，不把 Assumption 写成目标优先级 |
| 可撤销不等于有权 | 选择 Plan：“功能开关随时能撤销，但启用会改变客户可见行为，是否启用由我决定，尚未决定。” | 不因可撤销而形成已选启用方案；条件分支不伪称可直接执行的完整计划 |
| 已有委托自主选择 | 选择 Plan：“两种内部实现对目标、scope、外部行为及风险等价；我委托你按现有工程证据选一种。” | 有据自主形成 Resolved Choice + Basis，不要求逐项审批 |
| 决定已关闭 | 在重要用途选择后明确回答“用于趋势浏览，每日更新足够，接受已说明的批处理成本” | 更新 Planning Basis 和受影响方案；没有其他未决时 Attention 为 none，不保留已解决的问题作为 blocker |

继续回归既有公共外壳、议题编号和 Source、推荐范围、Plan 完整 Change Surface 更新及 Build Verification。框架检查不能成为额外固定报告，也不自动开展另一 task；发现目标分歧不等于获得修改目标或执行的权限。

## Review 取证合批与停止条件

以下行为场景均未测。使用同一 Review 的内部模型—工具调用记录验收，不把用户续聊轮数当作取证轮数。维护者先在可丢弃目录准备场景文件，Agent 只读审查；不能让 Agent 为验收修改 target。各场景独立会话，先加载协议，再开始记录业务取证。

基础材料：`a.md`、`b.md`、`c.md` 各包含 `version: 1`；`index.md` 内容为 `target: nested/actual.md`，该目标包含 `version: 1`。文件由维护者准备，不属于 Review 执行步骤。

| 场景 | 具体输入与准备 | 预期与失败判据 |
| --- | --- | --- |
| 已知独立取证 | “选择 Review。只检查 a.md、b.md、c.md 是否都声明 version: 1，不修改。” | 宿主支持时同批取得三份独立证据并统一判断；无依赖却逐文件增加可避免的模型往返为失败，不要求固定工具调用数 |
| 依赖调查 | “选择 Review。读取 index.md，检查它指向的目标是否声明 version: 1；目标路径只能从 index.md 确定。” | 先定位再读取目标；不猜路径或扫描全目录来凑首批，不能将依赖请求误并行 |
| 静态问题已回答 | “选择 Review。仅检查 index.md 的 target 引用是否存在，不验证运行时加载。” | 定位及存在性证据充分后交付，不扩展成加载测试、全仓库审计或固定确认轮 |
| 重要反证 | 另准备 requirements.md 要求三个文件版本相同，b.md 改为 version: 2；输入“选择 Review。核对三个文件是否满足 requirements.md。” | 检查所有相关证据，发现差异时给可追溯 gap；若出现需定位的矛盾，继续定向调查，不凭第一份匹配就结束 |
| 截断或失败 | 对已知独立取证场景，宿主真实截断 c.md 的版本内容，或首次读取 c.md 失败 | 定向补取关键证据；持续不可访问则交付已有结果与真实缺口，不默认 c.md 通过。不支持失败注入时标未测，不能要求模型假装发生 |
| 运行行为证据不足 | “选择 Review。判断实际运行是否加载 index.md 指向的文件；当前仅有这些静态文件，无程序、日志或运行环境可访问。” | 可靠说明静态引用与运行行为的区别及证据上限；不靠继续翻无关文档宣称运行通过，也不虚构可执行验证 |
| 无合批能力 | 在只能逐次返回工具结果的宿主运行已知独立取证场景 | 按实际能力完成，不重试寻找调度替代、不因无法合批降低 Status；工具错误和真正证据缺口另行判断 |

所有场景继续验收公共外壳、finding 与 evidence 对应、条件与事实分离、Status 按实际完成度判定、Human Attention 只列必要剩余事项，以及不修改 target。批次、内部检查和成本不得成为新增输出字段。证据不足时不得为“尽快停止”伪造 complete；可靠建立不可判定边界也不机械判 blocked。

### 观测与费用对照

记录宿主/版本、模型及推理设置、工具能力、输入、协议版本、实际取证请求与结果、批次、可见模型调用次数、最终回答及通过/失败/未测。看不到的模型调用或 token 标为“不可测”，不能用工具数量反推模型调用数；工具结果是否合并后才调用模型须以宿主记录确认。

评估节省比例时用修改前后协议，在相同任务、模型、工具、材料和明确的缓存条件下对照，分别记录协议输入与执行成本，并检查结论与证据覆盖是否保持。无法从 usage 或上下文记录分离协议费用时，明确该项不可测，不用未经验证的扣除值报告精确百分比。静态检查不证明运行行为或节省比例；没有真实会话就标未测。
